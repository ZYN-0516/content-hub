# 优化故事：任务中止为何必须"三层拦截"

> 这是面试时的核心故事模板。它来自一个真实缺陷：用户点击"中止生成"后，作品仍然被生成并落库。
> 所有数字均由 `tests/test_tasks.py::test_optimization_before_after_cancelled_task` 对照测试实测得出，非估算。

## 一、问题（用户视角）

创作台提交生成任务后，用户可以点"⏹ 中止生成"。优化前的表现：

- 前端立刻显示"已中止"，用户以为结束了；
- 后台 Celery worker 仍在调用百炼生成图片，生成完成后**建了一条 Content 记录**；
- 任务状态被覆盖回 `success`，"已中止"变成"生成成功"，作品还出现在系统里。

本质是**取消信号没有真正传到后台**，UI 与后台状态不一致。

## 二、根因

取消接口原本只做一件事：把数据库的 `status` 改成 `failed`。

- Celery 任务在worker内存中已经持有旧的 task 对象，看不到这个改动；
- 也没有保存 Celery 任务 ID，无法 `revoke`；
- worker 结束时无条件把状态写成 `success` 并落库，覆盖了取消结果。

三个环节（撤销、阶段检查、状态回写）全部缺失。

## 三、改法

| 环节 | 优化前 | 优化后 |
|---|---|---|
| 取消信号 | 只改数据库状态 | 创建任务时把 `celery_task_id` 写进 `parameters`；取消时 `revoke`（`terminate=False`，避免 solo worker 被杀） + 写 `parameters.cancelled=True` |
| 生成前 | 无检查，直接调 AI | 从 DB 重读取消标记，已取消则早退 |
| 下载前 | 无检查 | AI 出图后再次检查，已取消则不落盘 |
| 落库前 | 无检查 | 第三次检查，已取消则不建 Content、不覆盖状态 |
| 状态回写 | 早退时停在 `running` | `_cancel_result()` 显式写回 `failed`（本轮评测时又发现并修复的二次缺陷） |

关键点：**取消标记从数据库读，不依赖 worker 内存里的旧对象**；三处检查覆盖"排队中 / 生成中 / 出图后"三个时间窗。

## 四、可量化结果（对照测试实测）

对照方式：同一个测试里，用 `patch("_is_cancelled", return_value=False)` 模拟优化前（worker 不检查取消标记），与优化后走真实检查逻辑对比。

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| AI 接口调用次数 | 1 | 0 | 减少 1 次（省一次百炼费用） |
| 图片下载次数 | 1 | 0 | 减少 1 次 |
| 新建 Content 条数 | 1 | 0 | 不再产生幽灵作品 |
| 最终任务状态 | `success`（错误） | `failed`（正确） | UI 与后台一致 |
| 取消后是否覆盖结果 | 是 | 否 | 消除状态翻转 |

复现命令：

```cmd
venv\Scripts\python.exe -m pytest tests/test_tasks.py::test_optimization_before_after_cancelled_task -v
```

## 五、面试怎么讲（30 秒版）

"我在做内容生成平台时，用户反馈点中止后作品还是会出现。根因是取消只改了数据库状态，Celery worker 内存里是旧对象，而且我没存任务 ID，撤不掉；worker 跑完又把状态覆盖回成功。我的方案是创建任务时记录 Celery ID，取消时 revoke 并在 JSON 参数里写取消标记，worker 在生成前、下载前、落库前三处从数据库重读这个标记，命中就早退并显式把状态落回 failed。我还写了一个对照测试，模拟优化前不检查的情况：优化前会调用 1 次 AI、落库 1 条内容、状态被错误覆盖；优化后这三项全部归零。后来做评测时又发现早退会停在 running，补了一次状态回写。"

## 六、可延伸的追问点

- **为什么 `terminate=False`？** 本地用 `--pool=solo` 单进程 worker，`terminate=True` 会杀掉整个 worker，影响其他任务；靠数据库标记而非强杀进程更稳。
- **为什么从数据库读标记？** worker 启动时反序列化的 task 对象是旧快照， Celery 不会自动同步数据库改动。
- **三处检查是否冗余？** 不冗余，分别覆盖排队阶段、AI 生成耗时阶段、出图后到落库的窄窗口；这是典型的时间-of-check-to-time-of-use 问题。
