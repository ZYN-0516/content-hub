# content-hub：管理员任务视图改动与测试记录

> 记录日期：2026-11-24
> 范围：登录/注册页面化 → 任务中止 → 审核发布闭环 → 管理员「我的任务」分区及后续权限修复。

---

## 一、背景与目标

项目定位从「AI 生成工具」升级为「内容生成管理系统」，需要补齐三块能力：

1. 登录/注册从首页弹窗改为独立页面路由，注册有正则校验和错误提醒；
2. 生成中的任务可以被用户中止，且中止真正生效（不是只改数据库状态）；
3. 内容从「生成成功直接发布」改为「提交审核 → 审核员通过/驳回 → 进入广场」的闭环；
4. 管理员的「我的任务」区分**全站审核内容**与**自己创作的任务**，审核内容内部再分待审核/审核完成，管理员之间共享同一份审核记录。

---

## 二、需求澄清过程（避免理解偏差）

| 轮次 | 用户诉求 | 处理结果 |
|---|---|---|
| 1 | 管理员「我的任务」把待审核和其他分开 | 按管理员自己的任务做分组（理解偏窄，已废弃） |
| 2 | 要区分**审核内容**和**自己创作的任务**，审核内容分审核完成/待审核，管理员之间相通 | 改为全站审核记录 + 个人任务两大块 |
| 3 | 界面没变化 | 排查发现 `admin` 账号 `role=member`、`is_staff=True`，但用户信息接口未输出 `is_staff`，前端识别不出管理员 |
| 4 | 能看到别人取消的任务，不属于「我的」 | 生成任务列表/详情/取消接口改为始终只返回本人数据 |

## 三、代码改动清单

### 1. 用户与认证

| 文件 | 改动 |
|---|---|
| `apps/users/serializers.py` | `RegisterSerializer` 加用户名/密码 `RegexValidator`；`UserSerializer` 增加只读字段 `is_staff`、`is_superuser` |
| `apps/users/views.py` | 登录接口在 JWT 中附带 `user` 数据 |
| `config/urls.py` | 新增页面路由 `/login/`、`/register/` |
| `templates/login.html`（新增） | 独立登录页，提交成功后写入 JWT 并跳回 `?next=` 指定页面 |
| `templates/register.html`（新增） | 独立注册页，前端正则 + 确认密码 + 邮箱格式校验，失败页内红框提醒，成功跳登录页 |

账号/密码规则：

- 账号：`^[A-Za-z][A-Za-z0-9_]{3,19}$`（字母开头，4–20 位）
- 密码：`^(?=.*[A-Za-z])(?=.*\d)[A-Za-z0-9_@#$%^&*+=!?.\-]{8,20}$`（8–20 位，含字母和数字）

> 注意：Django 自带的「常见密码」检查仍然生效，例如 `Abc12345` 会被拒，正则通过不代表一定注册成功。

### 2. 任务中止

| 文件 | 改动 |
|---|---|
| `apps/core/views.py` | 创建任务时把 Celery task_id 写入 `parameters`；cancel 接口写 `cancelled=True` 标记并 `revoke`；任务详情/取消只允许本人操作 |
| `apps/core/tasks.py` | 生成前、下载前、落库前检查取消标记，取消后不再调用 AI、不创建 Content、不覆盖状态 |

> 原来的 bug：只改数据库状态，Celery 任务仍会跑完并把状态覆盖回「成功」，还照样生成内容。

### 3. 审核闭环

| 文件 | 改动 |
|---|---|
| `apps/core/permissions.py`（新增） | `IsReviewer`：管理员（`is_staff`）或 `role in (reviewer, admin)` 可审核 |
| `apps/core/views.py` | 三个审核视图换用 `IsReviewer`；新增 `POST /api/content/{id}/submit-review/`（draft/rejected → pending 并创建 ReviewTask）；审核列表支持 `?status=all` |
| `apps/core/serializers.py` | `ReviewTaskSerializer` 增加 `content_title`、`content_file`、`author_name`、`reviewer_name` |
| `apps/core/urls.py` | 注册 `content/<id>/submit-review/` 路由 |

`GET /api/review/tasks/` 默认仍只返回待审核（审核中心页面不受影响）；`?status=all` 返回全站审核记录，待审核排前、已处理按时间倒序。

### 4. 管理员「我的任务」视图与数据隔离

| 文件 | 改动 |
|---|---|
| `templates/index.html` | 移除弹窗登录，按钮改路由跳转；401 自动跳登录页；创作结果按钮改「提交审核」；新增审核中心页签；`loadTasks()` 按身份渲染；新增 `refreshUser()` 启动时刷新本地用户缓存 |
| `apps/core/views.py` | `GenerationTaskListCreateView.get()` 与 `_get_task_for_user()` 改为**始终** `filter(user=request.user)`，管理员也不能查看/取消他人任务 |

管理员视图最终结构：

```
我的任务
├─ 🛡 审核内容（全站共享，所有管理员看到同一份记录）
│   ├─ ⏳ 待审核：作品 / 作者 / 提交时间 + 「去审核」按钮
│   └─ ✅ 审核完成：通过/驳回徽章 + 审核人 + 时间 + 驳回意见
└─ 🎨 自己创作的任务：仅当前账号本人生成的任务
```

普通用户视图不变，仍为原来的平铺任务列表。

## 四、接口变更速查

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/users/login/` | 返回 `{access, refresh, user}`，user 含 `role` / `is_staff` |
| POST | `/api/users/register/` | 正则校验，失败返回中文原因 |
| GET | `/api/users/me/` | 当前用户信息，用于页面启动时刷新缓存 |
| GET | `/api/generation/tasks/` | **仅本人任务**（管理员也一样） |
| POST | `/api/generation/tasks/{id}/cancel/` | **仅本人任务**，写取消标记 + revoke |
| POST | `/api/content/{id}/submit-review/` | 提交审核 |
| GET | `/api/review/tasks/` | 待审核列表（审核员/管理员） |
| GET | `/api/review/tasks/?status=all` | 全站审核记录（含已处理、审核人、意见） |
| POST | `/api/review/tasks/{id}/approve/` | 通过并发布 |
| POST | `/api/review/tasks/{id}/reject/` | 驳回，可带 `comment` |

统一响应格式：`{code, message, data}`，前端取 `data`，错误信息取 `message`。

### 5.2 接口验证（事务回滚，不污染真实数据）

采用临时脚本：`django.setup()` 后在 `transaction.atomic()` 内造数据、调 API、断言，最后抛自定义异常强制回滚，并在 `finally` 中删除脚本。覆盖场景：

1. **审核闭环**：普通用户提交 → 内容 `pending` + 生成 ReviewTask → 重复提交被拒（400）→ 普通用户访问审核列表 403 → 管理员通过 → `published` → 广场可见。
2. **审核员权限**：`role=reviewer` 的非 staff 用户可以审核；驳回后作者重新提交会生成第二条审核记录，保留历史。
3. **全站记录共享**：一个 reviewer 通过、一个 staff 驳回后，两个管理员调用 `?status=all` 得到**完全相同**的记录；`reviewer_name`、`comment` 正确；默认列表不含已处理记录；普通用户 403。
4. **任务归属隔离**：管理员的任务列表只含自己的任务；直接 GET/取消别人的任务均返回 404。
5. **注册/登录/取消**：合法注册成功、重复用户名被拒、弱密码（常见密码）被拒、登录成功、建任务 → 取消 → 触发 revoke → 二次取消返回 400。

全部 PASS。测试产生的数据均已回滚，临时脚本/测试文件已删除。

> 测试坑：用 `create_user()` 造多个用户时不传 `email`，会因空字符串重复触发唯一约束，需要给每个用户不同 email。

## 六、注意事项

- 改 `.py` 后必须重启 `runserver`；Celery 的 `tasks.py` 改动还需要重启 worker：
  `celery -A config worker -l info --pool=solo`
- 页面启动时 `refreshUser()` 会用 `/api/users/me/` 覆盖 localStorage 里的用户缓存，所以旧的登录数据不用重新登录也能识别管理员。
- `admin` 账号的 `role` 仍是 `member`，管理员身份由 `is_staff=True` 判定，这是前端 `isReviewer()` 能识别的。
- 头像/图片走本地 `media/` 存储（MinIO 未启用），需要 `runserver` 运行才能访问 `/media/...`。
- 生成接口的「画面风格」输入框目前未拼进 prompt，所有描述需写在「画面描述」框里。
