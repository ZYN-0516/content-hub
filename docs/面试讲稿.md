# Content Hub 面试讲稿（5 问）

> 用法：每个问题先记"要点"，再用自己的话讲一遍，不要背。括号里是可量化数据，来自 `pytest` 与 `bench` 实测。
> 整体定位：**一个带完整内容生命周期的 AI 生成管理系统**，不是单页生图工具。

---

## 问题 1：这个项目解决什么问题？

**要点**

- 单点生图页面缺少用户体系和内容生命周期，不构成"系统"。我把一句话生成图片扩展成完整管理闭环：登录 → 创作 → 提交审核 → 发布广场 → 评论互动 → 后台管理。
- 生成耗时不可同步等待，做成 Celery 异步 + 前端轮询，页面不卡死，还能中途取消。
- AI 生成内容需要审核才能公开，用状态机和角色权限控制谁能看、谁能审、谁能改。
- 管理员和普通用户的数据范围必须隔离，"我的任务"在任何身份下都只返回本人的。

**30 秒回答**

"我做的是一个 AI 内容生成管理平台。它解决的问题是：单纯一个生图页面没有用户体系、没有内容生命周期，只能算工具不算系统。所以我围绕一句话生成图片，补上了注册登录、异步任务、审核发布、广场评论和个人中心，再叠加一套按角色区分的管理后台。技术上用 Django + DRF 做接口，Celery + Redis 处理耗时的生成任务，前端轮询状态并支持中途取消。最后用权限和数据隔离保证普通用户、审核员、管理员、超级用户看到的范围不同。"

## 问题 2：技术选型依据是什么？

**要点**

- **Django + DRF**：自带 ORM、认证、admin，能快速把"用户 + 内容 + 权限"这套模型落地；DRF 的序列化与权限类正好对应状态机。
- **MySQL 8**：关系型模型（任务/作品/审核/评论）关联清晰，事务用于审核状态流转的原子性。
- **Celery + Redis**：文生图要几十秒，必须异步；Redis 做 broker 足够轻。Windows 本地用 `--pool=solo`，因为 prefork 在 Windows 起不来。
- **原生 JS 单页**：项目目标是全栈能力展示，前端不追求框架，把精力放在后端状态机和权限。
- **本地 media + storage 抽象**：MinIO 拉取受限，先用本地文件，但用 `apps/common/storage.py` 抽象 `save_generated_file()`，以后换 OSS 只改一处。

**30 秒回答**

"选型围绕'快速落地一套带权限的内容系统'。Django + DRF 的 ORM、认证和权限类能直接表达用户、作品和审核状态机；MySQL 存关系数据，审核状态变更用事务保证原子性。文生图要几十秒，所以用 Celery + Redis 异步，前端轮询；本地 Windows 环境用 solo 池。前端我故意用原生 JS，把重心放在后端的异步和权限设计。存储层做了抽象，虽然现在落本地文件，但换 OSS 只需改一个函数。"

## 问题 3：最难的技术点是什么，怎么解决的？

**要点**（这就是优化故事，详见 `优化故事_任务中止.md`）

- 难点：用户中止后，Celery worker 仍继续生成并落库，把状态覆盖回成功，"已中止"变"生成成功"。
- 根因：取消只改数据库状态，worker 内存里是旧对象；没存任务 ID，撤不掉。
- 方案：创建任务时记录 `celery_task_id`；取消时 revoke + 写 `cancelled` 标记；worker 在生成前、下载前、落库前三处**从数据库重读**标记，命中就早退并显式把状态写回 `failed`。
- 可量化（对照测试实测）：优化前 AI 调用 1 次、落库 1 条、状态被错误覆盖；优化后三项全部归零。
- 二次发现：早退时状态停在 `running`，前端永远"生成中"——补了 `_cancel_result()` 显式写回 `failed`。

**40 秒回答**

"最难的是任务中止的一致性。用户点中止后，worker 还在跑，跑完把状态覆盖回成功，作品还会落库。根因是取消只改了数据库，worker 内存里是旧对象，而且我没存 Celery 任务 ID，撤不掉。我的方案是创建任务时把 Celery ID 写进参数，取消时 revoke 并写取消标记，worker 在生成前、下载前、落库前三处从数据库重读标记，命中就早退，并显式把状态落回 failed。我写了对照测试：模拟优化前不检查的情况，会调用 1 次 AI、落库 1 条内容、状态被错误覆盖；优化后这三项全部归零。后来做评测又发现早退会停在 running，补了一次状态回写。这个过程让我对异步任务的时序和状态一致性理解深了很多。"

## 问题 4：你怎么衡量效果？

**要点**

- 两层衡量：**接口正确性**用 pytest，**生成流程**用评测集。
- pytest：35 项测试，覆盖注册正则、登录、任务隔离与中止、审核闭环、角色权限、搜索评论、service 异常流程，全部通过。
- 评测集：20 条 prompt，自动统计成功率/平均耗时/P95，异常用例单列；当前 Mock 基线行为正确率 100%，平均 0.02s、P95 0.13s。
- 诚实说明：Mock 是流程基线，不是模型质量；真实语义质量需要 `--live` 后人工核对 `expect` 字段。
- 优化效果可量化：中止缺陷从"1 次调用 + 1 条落库 + 状态错误"降到全零。

**30 秒回答**

"我从两个维度衡量。第一是正确性：用 pytest 写了 35 个测试，覆盖注册校验、任务归属隔离、中止、审核状态流转、角色越权和 service 异常分支，全部通过。第二是流程质量：建了 20 条 prompt 的评测集，统计成功率和耗时分位数，异常输入单列。当前 Mock 基线行为正确率 100%，但这只说明流程通，不代表模型生成质量——那部分需要真实调用后人工核对，我在结果里留了人工评分列。另外优化前后我用对照测试量化了中止缺陷，从一次无效调用加一条幽灵作品降到零。"

## 问题 5：如果再有一周你会改进什么？

**要点**（按优先级，体现取舍判断）

1. **真实评测 + 提示词优化**：跑 `--live` 拿到真实成功率与耗时，针对失败用例优化 prompt，这是面试最有说服力的"优化前→后"素材。
2. **视频生成接入**：把占位的视频任务接上百炼视频模型，让动态描述（光点、丝带）真正生效。
3. **存储与部署**：本地 media 换成 OSS，配合多副本 web；补真实域名与 HTTPS，采集功能截图和 Demo 视频。
4. **前端体验**：「画面风格」目前未拼进 prompt，接上它；引入前端路由替代 `data-page` 切换。
5. **工程化**：加 CI 跑 pytest，补更细的异常测试（并发审核、重复提交竞态）。

**30 秒回答**

"如果再有一周，我会先做真实评测，跑一次 live 模式拿到真实成功率，再针对失败用例优化提示词——这比再加功能更有价值，因为它能给出可量化的优化故事。第二是接视频生成，现在视频是占位的，提示词里的动态描述还没生效。第三是工程化收尾：把本地存储换成 OSS 以支持多实例，补 CI 自动跑测试，再采截图和录 Demo 视频。前端方面会把'画面风格'真正拼进 prompt，并用路由替代现在的状态切换。我会优先做能量化、能展示的部分，而不是堆功能。"

## 附：可能被追问的点

- **为什么用 `--pool=solo`？** Windows 下 Celery prefork 起不来；solo 单进程，配合数据库取消标记，`revoke(terminate=False)` 不需要杀进程。
- **审核和角色怎么对应？** `IsReviewer` 认 `is_staff` 或 `role in (reviewer, admin)`；`IsAdmin` 认 staff 或 role=admin；用户角色管理单独用 `IsSuperUser`，只允许超级用户增减管理员/审核员。
- **状态机怎么保证不脏写？** 审核通过/驳回用 `transaction.atomic()` + `select_for_update()` 锁住审核记录，重复处理直接返回 400。
- **数据隔离怎么做的？** 任务列表和详情强制 `filter(user=request.user)`，管理员也不看别人的任务；全站数据只通过独立的审核/管理接口按权限开放。
